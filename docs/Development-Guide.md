# Порядок разработки и проверок

Перед началом выбрать историю со снятыми критическими вопросами и проверить ее зависимости. Изменения вести в отдельной ветке с понятным назначением, с префиксом feature/ для новой функции или fix/ для исправления. В Pull Request связать Issue, описать изменение, проверки и оставшиеся ограничения. Commit и push выполняются только при отдельном поручении владельца.

## Проверки
Для ввода проверяются границы, пропуски, нечисловые значения и сохранение формы. Для решателя нужны независимые контрольные задачи, условия на оси и границах, исследование сетки и временного шага. Для MPI сравниваются одинаковые входы на нескольких количествах процессов; цель 0,01 °C сохраняется, метрика утверждается до приемки. Время и ускорение измеряются отдельно от корректности с записью среды и повторов. Физическая проверка использует контрольные данные и целевой предел 5 % из отчета после определения метрики.

Для критериев проверяются нарушение, равенство, отсутствующий предел и неполный результат. Для сравнения проверяются несовместимые входы и отсутствие кандидатов. Для хранения проверяются ошибка записи и связи версий. CSV читается независимым средством; пропуски отличаются от нулей. Сквозной набор покрывает нормальный путь, отмену, ошибку MPI и отсутствие допустимого режима.

## Работа с данными
Сохранять версии модели, решателя и схемы; не менять входы уже запущенного задания. Показывать единицы и происхождение свойств. Демонстрационные значения явно маркировать. Не добавлять управление оборудованием и не выдавать результат модели за эксплуатационный допуск.

## Документация
Изменение требований сопровождается обновлением Issue, спецификации и таблицы соответствия. Поля Project сверяются с карточкой. Оценка родителя не складывается с трудоемкостью его частей. Решения по открытым вопросам записываются вместе с основанием и автором согласования.
